# Agent loop 与 Deep Agents 升级设计（v1，2026-10-19）

## 1. 背景与原则

py1–py9 的在线运行说明，生成层的主要瓶颈已经不在"第一次写得对不对"，而在"出错之后能不能自己改对"。现在的修复是固定的三轮：
- 编译报错，把这一块的问题发给模型，模型重写这一块；
- 模型看不到运行结果，也无法验证自己的假设；
- py9 中，同一份修复提示原样发了三次。

另一方面，有几类问题只能靠运行发现，例如：
- 接敌只在一个状态里处理；
- 等待确认没有超时；
- 想定时间估算错误。

因此本设计把"会出错、但有确定性检查器"的环节改成 agent loop。

**原则：agent 提出方案，确定性检查器做最终判定。**
- 编译器、IR 规范化、能力规则匹配、后端代码生成、确认闸门保持确定性，作为工具和最终关卡。
- 每个 loop 都必须以确定性检查结束，并有步数和时间预算。
- 防作弊约束写在工具层，不只写在提示词里。
- 所有改动记入运行记录（trace），并在审查报告中列出。

## 2. 全链路评估

| 环节 | 现在的形态 | 适合度 | 适合的 loop 和检查器 |
| --- | --- | --- | --- |
| C1 任务画像、C2 研究规划 | 单次调用 | 中 | 单次调用够用；可以让 C3 的结果回头修正规划 |
| C3 检索与证据包 | 固定步骤加缺口补检 | 高 | 研究型 agent：按维度并行检索、阅读、判断证据等级，直到满足 Falcon 门槛。检查器是门槛明细和覆盖表 |
| C4 战术提出、能力标注 | 单次生成加规则核对 | 中 | 先提出，再对照能力目录核对，不可行就自行改写 |
| C5 红队评审→回应→复核 | 固定流程 | 高 | 红队与蓝队两个子 agent 对抗，直到没有新的高危反制；反制直接转成 L3 想定 |
| Falcon 写战术稿 | 三次调用加固定三轮修复 | 最高 | `falcon fix`（P0，见 §4）。检查器是编译、L2、反应探针、L3 |
| Falcon 写验证块 | 与写行为树共用上下文 | 高 | 独立的测试设计子 agent，不看行为树（参照 AgentCoder 的结论） |
| 对抗想定 / 证伪 | 未做 | 高 | 搜索敌方位置、时机、干扰强度，找出能让期望失败的组合 |
| IR 构建、确认闸门 | 确定性，需人工确认 | 低 | 保持确定性；agent 只把待确认项整理成问题清单 |
| 参考值调参 `ir sweep` | 网格扫描 | 中 | 搜索交给优化算法，agent 负责解读结果、提出约束调整 |
| 能力缺口→开发 | 登记后由人开发 | 高 | 开发型 agent：写 AFSIM 脚本或插件草稿，运行验证后交人审核 |
| 后端：Mermaid、BT.CPP、二维仿真 | 确定性生成 | 低 | 保持模板生成 |
| 后端：AFSIM | 未开始 | 高 | 生成、AFSIM 解析、运行、与二维仿真轨迹对照（一致性检查）的 loop |

## 3. 接入 Deep Agents 的方式

工程已经依赖 `deepagents>=0.7.23`（`agent.py` 中有一个空壳 agent）。对应关系如下：

| 框架能力 | 在本工程中的用途 |
| --- | --- |
| 规划 + 主 agent（注：0.7.23 默认中间件没有 write_todos，由 `build_agent` 显式加入 TodoListMiddleware） | 按"需求→Crow→Falcon→IR→能力核对→后端"推进，失败时回到对应环节 |
| 子 agent（task） | 研究员、红队、战术稿作者、测试设计者、核查员、AFSIM 编码员；上下文相互隔离 |
| 工具 | 各个确定性步骤：Crow 门槛、`falcon check / try_tick / simulate / patch`、`ir build`、能力核对、后端导出。只返回摘要，完整产物写入文件 |
| 文件后端与权限 | 以模型包目录为工作区；只允许写入新的模型包目录；`_local/` 只读 |
| Skills | 写法说明、协同模式规则、按平台类别的示例改成按需加载的 SKILL.md。解决"提示词过长"和"协同知识散在三处" |
| 记忆 | 历次运行的常见错误；通过编译的战术稿作为少样本示例 |
| interrupt_on | 战术选择、`confirmations.yaml`、缺口处置，以及修复 loop 中 `ask_human` 提出的问题 |
| checkpointer | 长流程（Crow 30–60 分钟）中途失败后续跑 |
| 上下文压缩 | 长 loop 只保留笔记和最近几步的结果 |

## 4. P0：`falcon fix` 自检纠错循环

### 4.1 用法

```text
python -m afsim_research_agent.falcon fix <模型包> [--out <新目录>] [--max-steps 20] [--with-l3]
```

- 默认把模型包复制到 `<模型包>_fix` 再修改，原包不动。
- 结束时写回得分最高的版本，并执行一次 `falcon compile` 等价的完整重建。
- 生成两样记录：
  - `fix_log.json`：每一步的想法、动作、参数摘要和结果摘要；
  - 审查报告中的"自检修改记录"一节：每处改动的前后文本和理由，供人核对。

### 4.2 每一步的协议

模型每一步输出一个 JSON：`{"thought": "...", "action": "<工具名>", "args": {...}}`。程序执行工具，把结果摘要返回给模型，循环直到满足以下任一条件：
- `check` 通过（启用 `--with-l3` 时 L3 也要通过）；
- 模型调用 `finish` 或 `ask_human`；
- 用完预算。

这里不依赖原生函数调用，沿用现有的 JSON 模式，以避开 qwen 函数调用可靠性的风险。工具函数的接口与 LangChain tool 保持一致，P1 可以直接接入 Deep Agents。

### 4.3 工具

| 工具 | 参数 | 返回 |
| --- | --- | --- |
| `check` | — | 状态和得分；按块列出问题（编号、行号、说明）；启用 L3 时附未通过的期望 |
| `show` | `block` | 该块全文，带整份战术稿中的行号 |
| `guide` | `block` | 该块的写法说明（与生成时使用的说明相同） |
| `explain` | `problem` | 问题全文，加上相关的转换清单、可引用的名字、测试输入提示 |
| `try_tick` | `role, state, given` | 用临时测试跑一拍，返回下一状态、触发的转换、动作和消息，用来验证假设 |
| `patch` | `block, old, new` | 在块内唯一匹配处替换；改完自动重新检查，返回问题数的变化 |
| `replace` | `block, text` | 整块重写（大改时使用），同样自动重新检查 |
| `revert` | `block` | 恢复为本次修复开始前的文本 |
| `finish` | `summary` | 结束 |
| `ask_human` | `question` | 结束，把问题写入审查报告交人决定 |

### 4.4 防作弊约束（工具层强制执行）

- 验证块中测试的数量、想定的数量、想定期望的数量都不能比开始时少；违反时拒绝修改，并说明原因。
- 不能新增 `user_specified` 依据，因为它只能来自需求原文。
- 每次修改都记录前后文本；审查报告逐条列出，交人核对。

### 4.5 得分与回退

- 得分为（检查走到的阶段，问题数，L3 未通过数），越小越好；始终保留得分最好的版本。
- 某次修改让得分变差时，不自动撤回，而是在返回结果里提示"变差了"，由模型决定是否 `revert`。结束时取得分最好的版本。

### 4.6 上下文

每一步的提示包含：
- 规则与工具说明；
- 当前检查摘要；
- 模型自己的笔记（thought 的累积，保留最近若干条）；
- 最近 6 步的动作和结果。

块的全文只在模型调用 `show` 时提供，所以提示长度基本恒定，约 6–10k 字。

## 6. 风险

| 风险 | 对策 |
| --- | --- |
| 成本与时延 | 按环节分配模型；每个 loop 设步数和时间预算 |
| 可复现性 | 每一步写入运行记录；最终是否通过只由确定性检查决定 |
| 为了通过而作弊 | 工具层强制约束，审查报告逐条列出改动 |
| 函数调用可靠性 | 采用 JSON 动作协议；P1 接入 Deep Agents 前先实测 qwen 的函数调用 |
| 资料安全 | 检索工具在工具层过滤本地受控资料、想定数据和平台参数，不只靠提示词约束 |

## 7. 实现状态（2026-10-19）

P0 已实现：
- 代码：`falcon/sheet/fixer.py`（`SheetFixer` 工具集、`fix_package` 循环、日志），CLI 子命令 `falcon fix`；`recompile.py` 拆出 `Workspace` / `open_workspace`，供 `fix` 与 `compile` 共用。
- `fix:*` 阶段使用 JSON 模式（`args` 是自由对象）。
- 提示中给出需求条款、选定战术摘要、块目录（含行号范围）、当前问题、笔记和最近 6 步；块全文只在 `show` 时给出。实测 py9 包上每步提示约 2.5–5k 字。
- `try_tick` 在临时副本中注入测试 `zz_try_tick` 跑一拍，不改稿件；稿件尚不能跑 L2 时直接说明。
- 测试：`tests/unit/falcon/test_falcon_fix.py`（脚本化 agent）。覆盖以下几点：
  - 修复成功；
  - 删除测试被拒绝；
  - `old` 不唯一时提示；
  - 得分变差时提示，结束时写回最好的版本；
  - `ask_human` 写入审查报告；
  - 原包不变。

2026-10-19 提效（见 `docs/analysis/2026-10-19-agent-loop-efficiency.md` 与 surface-formats §10.14）：
- 新增问题卡片、快速修复（`apply_fix`）、复合编辑（`edit`，含测试自动生成和编辑拦截）；
- 由程序维护的进度表（含失败做法与"反复未解决"提示）；
- 运行指标（`fix_log.json` 的 `metrics`）。

尚未做（留给在线评测后再定）：
