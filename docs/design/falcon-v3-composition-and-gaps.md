# Falcon v3：上层组合与缺口委托设计稿

> 状态：草案（2026-10-30）
> 基于：`tactical-behavior-ir-v2-layered.md`（七层与方案 B）、`capability-catalog-integration-v1.md`（动作集 / 战术集）、`falcon-surface-formats-v2.md`（战术稿）
> 对应 IR 2.0 计划第 6 步

## 0. 背景与目标

IR 2.0 把模型分成七层，模型只写上三层：子树、状态树、任务状态机。下面各层由程序引用、推导、校验。三车编队的战术集路径已在 AFSIM 中跑通，与手写版一致，说明"引用现有子树、组合成状态树和任务状态机"可行。

Falcon v3 的目标：

1. 由需求生成 IR 2.0 的上三层，**优先引用和组合能力集里已有的子树与动作**。
2. 缺少的子树和能力，**写成带契约的缺口**，交给其他 agent 实现，Falcon 不去猜它们的语义。
3. 缺口未补齐时，Falcon 的模型也能先做 L1 校验，并用理想化语义跑 L2 和二维仿真。
4. 缺口补齐后，用同一份契约验收，再接 AFSIM 编译、运行、对比。

不在本稿范围：

- 能力开发 agent 如何写 AFSIM 原生代码。本稿只定它的输入、输出和边界。
- 战术集本身的修订流程。

## 1. 分工

| 角色 | 输入 | 输出 | 能接触的资料 |
| --- | --- | --- | --- |
| Falcon | 需求、Crow 选定的战术、能力集（动作 ID、参数、契约描述、战术集条目） | IR 2.0 模型包（上三层、新增黑板字段、参数、假设、测试、想定）与缺口登记 | 与现在相同：不含原生名称、绑定、脚本、路径 |
| 子树 agent | 子树缺口契约、能力集 | 一个 IR 2.0 子树及其 L2 测试 | 与 Falcon 相同 |
| 能力开发 agent | 能力缺口契约、本地工程 | 新的原生叶节点或脚本、绑定条目、能力集条目、测试 | 本地工程；只在本地运行 |
| 编排器 | 以上各方的产物 | 缺口状态、重新校验与 AFSIM 回归的结果 | 不读内容，只调度 |

```
需求 ─► Falcon ─► 模型包（上三层 + 占位） ──► L1 / L2 / 二维仿真（理想化）
                    │
                    ├─ 子树缺口 ─► 子树 agent ─► 子树 + 测试 ─┐
                    └─ 能力缺口 ─► 能力开发 agent（本地）─► 叶节点 + 绑定 + 能力集条目 ─┤
                                                                         ▼
                              编排器：验收 → 重新导出能力集 → 替换占位 → L1–L3 → AFSIM 对比
```

## 2. Falcon 的输出

### 2.1 模型包内容

| 文件 | 内容 |
| --- | --- |
| `behavior_spec.yaml` | `ir_version: "2.0"`：`model`、`roles`、`missions`、`state_trees`、`subtrees`、新增的 `blackboard` 字段、`parameters`、`assumptions`、`tests`、`scenarios` |
| `gaps.yaml` | 缺口登记（§4），每条带契约 |
| `tactic_sheet.md` | 模型写的战术稿，供审阅和局部修复 |
| `review.md`、`trace.json` | 与现在相同；审阅页增加"引用了什么、新建了什么、缺什么"一节 |

以下内容 Falcon 不写，由规范化填写：`capability`（第 1 层）、`arbitration` 的推导部分（第 4 层），以及切片黑板字段的导入（第 3 层）。

### 2.2 各层由谁写

| 层 | Falcon 写什么 |
| --- | --- |
| 7 任务状态机 | 每个角色的状态、转换、事件；或者整体引用战术集任务，只覆盖其公开参数 |
| 6 状态树 | 状态 → 子树的映射 |
| 5 子树 | 引用战术集子树；用已有动作内联组合；或引用缺口占位 |
| 3 黑板 | 只声明切片里没有的新增字段，写条件表达式 |
| 2 动作 | 在叶节点上选动作集 ID、给参数；没有的动作登记为能力缺口 |
| 4 仲裁 | 只写例外的持有者 |

## 3. 引用、组合与新建的判定

### 3.1 判定顺序

对每个状态要做的事，Falcon 按下面的顺序选择，取第一个满足适配条件（§3.2）的：

1. **引用战术集任务**：整个角色的任务都能由战术集里的某个任务承担。
2. **引用战术集的子树或状态树**。
3. **内联组合**：用已有动作、条件和战术集子树，在本模型的 `subtrees` 里组合出来。节点数不超过 12 个、不可复用时，优先用这种方式。
4. **登记子树缺口**：需要的子树可以由已有动作组合，但逻辑复杂（多步、带重试或协同），或者明显可以复用，交给子树 agent 去做更合适。
5. **登记能力缺口**：至少需要一个能力集里没有的动作，即平台层面要新增功能。

第 4、5 步都要在 `gaps.yaml` 里写出理由：为什么第 1–3 步不行。

### 3.2 适配条件

引用之前，编译器按契约逐项核对，任意一项不满足就不能引用：

| 项 | 要求 |
| --- | --- |
| 平台类别 | 条目适用于该角色的 `capability_class` |
| 参数 | 需求要调的量都在条目公开的参数里；只能覆盖参数，不能改结构 |
| 黑板读取 | 条目读取的字段在该角色上有来源：切片导入、其他节点写入或外部事件 |
| 资源 | 与同一状态里并行的其他节点不冲突（ARB001 规则） |
| 结果语义 | 与状态的出边一致：若转换依赖"树成功 / 失败"，条目必须会结束；一直运行的条目只能配合事件或条件转换 |
| 语义 | 条目的说明与需求条款一致。这一项由模型判断，编译器只检查有没有写出对应的需求条款编号 |

"看起来相近"但不满足上表的，不能引用，只能走第 3–5 步。这条规则针对的是 v1 中出现过的"相似但不同"的替代。

### 3.3 不允许的做法

- 修改战术集子树的结构，或在引用时注入子节点。
- 在新建子树里嵌入脚本。
- 用一串已有动作去近似一个缺失的平台能力，却不登记缺口。确有临时替代时，要同时登记缺口，并把替代写进 `assumptions`。

## 4. 缺口登记

### 4.1 在 IR 中的写法

缺口在树中以占位节点出现，引用 `gaps.yaml` 中的编号：

```yaml
- {type: subtree, subtree: gap.bounding_overwatch, params: {bound_m: 200}}
- {type: action,  action:  gap.smoke_screen,       params: {duration_s: 30}}
```

- 前缀 `gap.` 表示占位；规范化按 `gaps.yaml` 中的契约检查参数、黑板和资源，与真实条目一样。
- 未补齐的占位报 **GAP001**（警告）：允许 L1–L3，结果标为"含占位"。
- AFSIM 编译遇到占位报 **GAP002**（错误），不生成。

### 4.2 子树缺口

```yaml
gaps:
  bounding_overwatch:
    kind: subtree
    description: 两组交替跃进，一组前进时另一组掩护
    reason: 战术集没有交替跃进；可用已有动作组合，但需要轮次协同，宜做成可复用子树
    clauses: [REQ-3, TAC-2]            # 对应的需求 / 战术条款
    roles: [leader, wing]
    capability_class: ground_vehicle
    params:
      bound_m: {type: double, unit: m, required: true, range: [50, 500]}
    blackboard:
      reads:  [target_valid, ir_group_index]
      writes: [ir_bound_phase]         # 新字段同时在 behavior_spec.blackboard 中声明
    resources: [movement]
    result:
      running: 正在跃进或掩护
      success: 两组都到达 bound_m 处
      failure: {codes: [BLOCKED, TARGET_LOST], meaning: 任一组受阻，或目标丢失}
      terminates: true
      max_duration_s: 180
    uses: [movement.move_to_point, formation.column_slots]   # 预期用到的已有动作，可空
    used_by: [leader.ADVANCE, wing.ADVANCE]                  # 占位所在的状态
    stub:                              # 补齐前，L2 和二维仿真按此执行
      success_after_s: 60
    acceptance:                        # 验收用 L2 用例：初始黑板、步数、期望结果
      - {id: reaches_bound, given: {target_valid: true}, ticks: 80, expect: success}
      - {id: target_lost,   given: {target_valid: false}, ticks: 5, expect: failure}
```

### 4.3 能力缺口

字段与动作集契约相同，这样补齐后可以直接写进能力集：

```yaml
  smoke_screen:
    kind: action
    description: 在本车前方施放烟幕
    reason: 能力集没有任何遮蔽类动作
    clauses: [REQ-5]
    capability_class: ground_vehicle
    params:
      duration_s: {type: double, unit: s, required: true, range: [5, 120]}
    lifecycle: {start: 下达后立即生效, running: 烟幕持续期间, cancel: 不可取消}
    completion: 持续时间到
    failure_codes: [NO_AMMO]
    resources: [launcher]
    blackboard:
      writes: [smoke_active]
    observable: 想定输出中可见烟幕开始和结束
    used_by: [leader.CONTACT_DEPLOY]
    stub: {success_after_s: 30}
    acceptance:
      - {id: smoke_completes, given: {}, ticks: 32, expect: success}
    local_only: true                   # 由编排器强制写入
```

- 能力缺口描述的是**需要什么**，不写原生名称、脚本或工程路径；这些由能力开发 agent 在本地决定。
- 缺口编号沿用现有规则（契约文本的哈希，`cap-gap-…`），同一能力在不同需求中得到同一编号，可以合并。
- 与 Crow 估计的能力缺口对照：命中的标为"已确认"，Crow 估计有但模型没用到的列入审阅页。

### 4.4 占位的理想化语义

| 层级 | 占位怎样执行 |
| --- | --- |
| L1 | 按契约校验参数、黑板、资源和结果语义（§3.2） |
| L2 | 按 `stub` 返回结果：`success_after_s`，或按用例指定；写入契约中的 `blackboard.writes` |
| 二维仿真 | 同 L2；占用资源；报告中标出"理想化：缺口 <编号>" |
| AFSIM | 不执行，GAP002 |

`stub` 只能用上面这几种写法，不能写成脚本。

## 5. 其他 agent 的职责与边界

### 5.1 子树 agent

- 输入：一条子树缺口及其契约、能力集。
- 输出：IR 2.0 子树，加上覆盖 `acceptance` 的 L2 测试。
- 验收：L1 通过；`acceptance` 全部通过；参数、黑板读写、资源与契约一致；二维仿真中替换占位后，Falcon 原有的测试和想定不退化。
- 子树先放进模型包，标为"本模型子树"。是否收进战术集，由人决定（§6.3）。
- 能接触的资料与 Falcon 相同，可以使用同一个模型服务。

### 5.2 能力开发 agent

- 输入：一条能力缺口及其契约，以及本地工程。
- 输出（全部写到新目录，不覆盖用户已有的 AFSIM 文件）：
  - 原生叶节点或脚本；
  - 绑定条目；
  - 能力集条目，内容为契约，需与缺口一致；
  - AFSIM 单项测试的输入文件和期望结果。
- 验收：AFSIM 单项测试通过；能力集重新导出后，L1 按新条目通过；`acceptance` 在 AFSIM 中通过。
- 边界：
  - 只在本地运行；原生名称、绑定和工程内容不进入公网请求、公共索引或云端模型；
  - 产物进入工程前必须经人审核，与这次战术集修改的做法相同：先备份，比较哈希后再写入。

### 5.3 产物的统一格式

两类 agent 交付时都附一份 `delivery.yaml`：缺口编号、产物清单、验收结果、契约差异（应为空；不为空时写明原因）。

## 6. 编排回路

### 6.1 缺口状态

```
open ─► assigned ─► delivered ─► accepted
                       │
                       ├─► rejected   （验收失败；带原因退回同一 agent，最多 2 次）
                       └─► infeasible （做不出来；退回 Falcon）
```

### 6.2 补齐之后

1. 能力缺口：重新导出能力集。`content_hash` 改变后，所有引用它的模型包都标为"需重新核对"。
2. 把占位 `gap.<id>` 换成真实的 ID 或子树，契约差异为空才自动替换。
3. 重新运行 L1、L2、二维仿真。
4. 所有缺口都补齐后，进行 AFSIM 编译、运行、对比，判定方法与第 5 步相同。

### 6.3 做不出来的缺口

退回 Falcon，同时附带约束"缺口 <编号> 不可用"。Falcon 有两种处理：

- 换一种组合，按 §3.1 重新判定；
- 采用替代方案，并写进 `assumptions`，在审阅页标出。

这个回路最多来回 2 轮；之后交给人决定。

### 6.4 人工确认点

- 能力开发产物写入工程之前。
- 子树收进战术集之前。
- 采用替代方案时：这属于需求降级，需要确认。

## 7. 安全

- Falcon 与子树 agent 的提示词只含：动作集 ID、参数、契约描述、战术集条目的 ID 和说明。不含原生名称、绑定、脚本、路径或想定数据。
- `gaps.yaml` 中能力缺口的内容同样只描述需求；编排器检查每条记录都有 `local_only: true`，只把它交给本地的能力开发 agent。
- 所有产物写到新目录；写入用户工程前比较哈希或修改时间，原文件先备份。
- 报告与审阅页不包含受控资料原文、密钥，也不包含未经清理的模型响应。

## 10. 待确认

1. 战术稿只保留 Python 写法，还是同时保留 XML？建议只保留 Python。
2. 内联组合的规模上限：本稿暂定 12 个节点。
3. 子树 agent 和能力开发 agent 首期是否由人代办，只实现接口和验收？建议这样做。
4. 能力开发 agent 使用什么模型：它会接触受控资料，只能是本地模型或由人完成。
5. 是否允许 Falcon 整体引用战术集任务：允许的话生成会很稳，但测不出模型自己写状态机的能力。建议两种都测：D 阶段分别跑"可引用"和"禁止引用任务"两种。

## 11. 实现说明（2026-10-30，A–C 阶段）

| 模块 | 内容 |
| --- | --- |
| `ir/v2/models.py` | `gaps: {id: Gap}` 代替原来的 `needs`；`Gap` 的字段见 §4，`stub` 只能写 `result`、`success_after_s`、`failure_code`、`writes` |
| `ir/v2/normalize.py` | `gap.<id>` 占位按缺口契约检查（参数、平台类别、黑板读写、资源、桩的写入）；每处占位报 GAP001 警告；能力缺口强制 `local_only: true`；`used_by` 由程序填写 |
| `ir/v2/runtime.py`、`sim/run.py` | 占位按桩执行，占用缺口声明的资源；L2 可用 `actions` 指定占位的结果；仿真报告列出"理想化缺口" |
| `ir/v2/afsim/compiler.py` | 有占位时报 GAP002，不生成；运行配置的 `[parameters]` 给出想定提供的参数取值 |
| `falcon/v3/pyexpr.py`、`pytree.py` | 条件表达式与树函数 → IR 2.0 |
| `falcon/v3/compiler.py` | 战术稿 v3 → `behavior_spec`（IR 2.0）与源码映射（IR 路径 → 块与行） |
| `falcon/v3/catalog.py` | 提示词中的能力集：结构稿看切片索引，控制稿看选中切片的动作契约摘要、战术集条目与黑板字段（不含请求编号、执行状态等接口字段） |
| `falcon/v3/prompts.py`、`draft.py` | 生成流程与模型包；`falcon draft3`、`falcon compile3` |

战术稿 v3 的块：`yaml model`（含 `slices`、角色可引用战术集任务）、`mermaid <角色>`、`python conditions`、`python <角色>`、`yaml gaps`、`yaml verification`。树函数名与状态名相同的是状态树，小写函数是子树；只调用一个战术集条目或子树的状态函数直接映射到它。

请求文件（`V3Request`）：`requirement`、`model_id`、`roles`、`scenario_parameters`（只把名称、类型和说明交给模型）、`allow_mission_ref`、`state_names`（与评测想定对齐时使用）、`slices`、`capability_set`、`max_repair`。

离线门槛 B：按 IR 2.0 编写的三车编队模型改写成 v3 战术稿后，编译结果与原模型逐状态等价（SHUTDOWN 由包一层子树改为直接映射到战术集状态树，行为相同）。

已知限制：

- 二维仿真没有编队动作的模型，这些动作按立即成功处理，依赖编队几何字段的条件按默认值判断；验证稿的提示词会说明这一点。
- 评测想定按状态名驱动目标（如进入保持距离状态后目标开始机动），所以模型自己写状态图时，用 `state_names` 给出与想定一致的状态名。

## 12. 在线闭环结果（D 阶段，三车编队，2026-10-30）

请求只给出需求文字、角色、想定参数名（路线）、想定事件名（`cancelled`）和与评测想定一致的状态名；模型输出经编译器、规范化、L1–L3 后编译到 AFSIM，与手写版对比。共运行 7 轮（作业 028–034），每轮按暴露的问题修改编译器或提示词。

| 作业 | 允许引用战术集任务 | 不允许引用 |
| --- | --- | --- |
| 033 | 引用正确，但规范化丢了引用任务带入的事件（已修正），AFSIM 编译失败 | **AFSIM 通过** |
| 034 | **AFSIM 通过** | 并行分支重复搜索，资源冲突（ARB001）未修好 |

两次通过的状态序列都是 ASSEMBLE_SEARCH@0 → SEARCH_ADVANCE@2 → CONTACT_DEPLOY@3 → STANDOFF_TRACK@22 → TARGET_LOST_HOLD@140 → STANDOFF_TRACK@144 → SHUTDOWN@147 → COMPLETE@149，与手写版顺序一致，想定标记全部出现，清理检查为真。展开早 10 s，是因为手写版进入搜索前进 10 s 后才开雷达；之后各转换早 4 s。这与战术集直接转换的结果相同。

模型做对的：每个状态都引用了合适的战术集状态树；触发条件照战术集任务的含义写；没有编造动作，没有不必要的缺口。

各轮修正（按出现顺序）：

- 条件只能读选中切片（含依赖闭包）的字段；
- 报错：枚举外的取值、无取值列表的字符串比较、接口字段、常量条件、自引用；
- 提示词给出战术集任务触发条件的含义；
- 引用任务时，与其触发同名且未被使用的条件、事件自动删去；未被使用的条件、事件只报警告；
- 想定事件名不一致报错；
- 二维仿真中停滞的状态退回状态图与条件修复；
- 修复后 L1 不通过时恢复修复前的稿子；
- 规范化后的模型保留引用任务带入的事件（此前引用任务的模型无法编译到 AFSIM）。

仍未解决：

- **稳定性**：同一请求两次运行，结果不同（各通过一次）。不允许引用时，模型有时在并行分支里重复写战术集树已包含的搜索，资源冲突的修复没有成功；需要在冲突提示中指出是哪个引用的战术集树已经包含了该动作。
- **L2 / L3 与 AFSIM 不一致**：二维仿真没有编队动作的模型，这些动作立即成功，横队到位条件按默认值立即成立，展开状态被连续转换跳过；模型写的测试与想定期望经过展开状态，因此不通过。AFSIM 通过的两个模型包仍标为 `draft_invalid`。需要给编队动作补二维仿真模型，或在理想化时让依赖字段保持"未到位"。
- **评测耦合**：状态名、外部事件名由请求给出，以对齐想定；路线名只以参数名交给模型。
